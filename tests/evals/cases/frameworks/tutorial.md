# 给仓库加一条自动测试流水线

## 从一次线上事故说起

上周三夜里，同事老周改了支付模块的一行代码，本地跑过就合进了主干。
第二天早上，退款接口挂了两个小时，客服电话被打爆。
这类事故的根因很简单：合码之前，没有人强制跑测试（见 fact_001）。

## 读完这篇你能做到什么

给任意一个 Python 仓库接入 GitHub Actions，每次 push 自动跑测试，失败直接红在提交记录里。

## 前置条件

- 一个 GitHub 账号，仓库已推送远端
- 仓库里已有 `pytest` 可运行的测试
- 本地装好 Git，会用基本的 add 与 commit

## 四步接好流水线

### 第一步：建目录与文件

在仓库根目录新建 `.github/workflows/tests.yml`，先写入最小配置：

```yaml
name: tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: pip install -e ".[dev]"
      - run: pytest
```

提交这个文件，push 到远端。

### 第二步：验证流水线真的跑了

打开仓库的 Actions 标签页，应看到一条名为 tests 的运行记录，状态是绿色对勾。
看不到记录，说明文件路径写错了，回上一步检查目录名。

### 第三步：故意弄红它一次

把某个测试断言临时改成 `assert 1 == 2`，push。
这次运行应显示红色叉号，并给出失败测试的完整输出。
没变红，说明触发器没配上，检查 `on:` 那一行。

### 第四步：恢复现场

还原断言，再 push 一次，记录变回绿色。
到这里，流水线就成了。

## 三个常见坑

- **pip 装不上依赖**：私有依赖需要 token，先把 token 写进仓库的 Secrets，再在 yml 里引用。
- **本地绿、远端红**：多数是 Python 版本差异，在 yml 里钉死 `python-version: "3.11"`。
- **跑得越来越慢**：给 pip 加缓存（`cache: pip`），大仓库能省一半时间。

## 下一步

流水线跑稳之后，可以接着加 lint、覆盖率门槛、合码保护规则。
一次加一样，每样都先让它红过一次。
