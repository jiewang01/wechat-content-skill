# 框架：tutorial（教程 / how-to）

> 适用：上手指南、工具教程、流程拆解、step-by-step 操作文。
> 输入：`ContentBrief`；输出：`ArticleDraft`（纯 Markdown，无 `:::` 标记）。

## 结构骨架

```text
1. 场景痛点   —— 一个具体的人/事/失败现场开头，不写「在当今时代」
2. 目标承诺   —— 读完能做成什么，一段话，可验证
3. 前置条件   —— 环境/版本/账号/知识门槛，用列表
4. 步骤正文   —— 每步：做什么 → 怎么做 → 验证成功 → 常见报错
5. 常见坑     —— 3-5 个真实易错点，每个给出解法
6. 总结与下一步 —— 学到了什么 + 顺着能做什么
```

## 写作规则

- **每一步必须可验证**：写「运行后应看到 X」，不写「这样就配置好了」。
- **命令与代码给全文**：读者复制即可跑；占位符用 `<your-name>` 形式并说明。
- **失败优先**：预计读者会卡住的地方，主动写出报错信息长什么样、怎么解。
- **版本钉死**：工具/库版本写进正文（如「Node 20+」），不写「最新版」。
- 每条事实性陈述（性能数字、兼容性、价格）必须挂 `fact_id`；没有来源就删掉或改成体验描述。

## 字数预算（word_target 参考）

| 部位 | 占比 |
|------|------|
| 场景痛点 + 目标 + 前置 | 15% |
| 步骤正文 | 60% |
| 常见坑 | 15% |
| 总结 | 10% |

## 自审清单（批判 → 重写阶段逐项过）

- [ ] 开头 100 字内出现了具体的人/事/数字吗？
- [ ] 每个步骤都有「验证成功」的标准吗？
- [ ] 命令和代码复制即可运行吗？版本写死了吗？
- [ ] 常见坑是不是真的常见（有依据或经验），还是凑数？
- [ ] 删掉任何一段，读者会迷失吗？（不会 = 该段可删）
- [ ] 跑过 humanize 检测器，`passed: true` 了吗？

## Humanize 专项提示

教程最容易踩的 AI 味：步骤开头全用「首先/其次/最后」；每段结尾强行总结「这样我们就完成了 X」。改法：直接以动词或对象开头（「打开设置面板」「报错 `ECONNREFUSED` 说明端口没起」）。
