# 框架：case-study（案例复盘）

> 适用：项目复盘、公司案例拆解、成败归因、「他们是怎么做到的」。
> 输入：`ContentBrief`；输出：`ArticleDraft`（纯 Markdown，无 `:::` 标记）。

## 结构骨架

```text
1. 结果先行   —— 一句话结局 + 关键数字，读者 30 秒知道答案
2. 背景与约束 —— 当时的条件、资源、deadline；不是流水账
3. 关键决策   —— 2-4 个转折点：当时的选项集、实际选择、为什么
4. 执行细节   —— 真正做了什么；可复用的操作，不是口号
5. 归因与教训 —— 哪些是能力、哪些是运气；换个场景还成立吗
```

## 写作规则

- **结果先行**：先给结局再讲过程，不要吊胃口吊到结尾。
- **决策点写选项集**：不只写「选了 A」，写当时还有什么选项、为什么否掉。
- **归因诚实**：区分「做对了」和「赶上好时候」；把运气写成能力是案例文最大的耻辱。
- **教训可执行**：每条教训是动词句，绑定具体场景；「正确的废话」删掉。
- **外推边界**：明确哪些结论只在案例的特殊条件下成立。
- 数字挂 `fact_id`；无法核实的数据标注来源属性（如「受访者口述」）。

## 字数预算（word_target 参考）

| 部位 | 占比 |
|------|------|
| 结果先行 + 背景约束 | 20% |
| 关键决策 | 35% |
| 执行细节 | 25% |
| 归因与教训 | 20% |

## 自审清单（批判 → 重写阶段逐项过）

- [ ] 第一段有结局和数字吗？
- [ ] 每个关键决策都写了当时的选项集吗？
- [ ] 教训是可执行的动词句，还是「坚持就是胜利」式空话？
- [ ] 有没有把运气写成能力？有没有把特例包装成通则？
- [ ] 换个行业的人读执行细节，能带走可复用的东西吗？
- [ ] 跑过 humanize 检测器，`passed: true` 了吗？

## Humanize 专项提示

案例复盘最容易踩的 AI 味：结尾升华「这告诉我们一个道理」；教训写成放之四海皆准的口号。改法：教训绑定具体动作——不说「重视用户反馈」，说「上线前 48 小时把客服群置顶，每 4 小时过一遍未回复消息」。
